# question-bank

Source of truth for every assessment question. **Questions live in code, not in the database**: Supabase only stores users, sessions, attempts, marks, timings and events.

```
question-bank/
  q_coding.js          16 DSA questions (hand-authored; includes dev-only `reference` solutions + `config.bench`)
  q_other.js           SQL / NoSQL / UI / MCQ questions (GENERATED by gen/build.js, don't edit by hand)
  gen/                 author_data.js (SQL, NoSQL), author_ui_mcq.js (UI, MCQ), lib.js, build.js (computes expected outputs)
  q_coding2.js         short coding questions added in v1.1 (2-4 min, exactly 10 tests: 3 visible + 7 hidden)
  q_ml.js              ML Workflow drag & drop `sequence` questions (subject `mlflow`)
  q_cloud.js           Cloud `architecture` + `match` drag & drop questions (subject `cloud`)
  interactive.js       generator helpers for the drag & drop types (opaque ids, deterministic shuffle, scoring units, authoring checks)
  fixtures/            dev-only fixtures for the validators (never shipped)
  questions.js         combines everything, assigns stable ids + subject slugs
  validate*.js         runs every reference solution against its tests (sql.js, mingo, optional jsdom); validate_interactive.js covers the drag & drop types
  test_*.js            unit tests (interactive marking + authoring checks)
  build.js             writes the two generated catalog files (below)
```
`npm run validate` runs every `validate_*.js` and `test_*.js` in this folder. Drag & drop contract and scoring: `docs/INTERACTIVE_TYPES.md`.

## Workflow
```bash
cd question-bank
npm install
npm run gen-other      # only after editing gen/author_*.js (regenerates q_other.js with computed expected values)
npm run validate       # all reference solutions must pass
npm run build-bank     # writes frontend/src/bank/questions.generated.js and backend/src/catalog.generated.js
```
Commit both generated files and deploy the **frontend and backend together** (they share `BANK_VERSION`).

## Ids and subjects
- Subject slugs: `dsa` (Programming (DSA)), `sql`, `nosql`, `ui` (Quick Dev), `aiml`, `mlflow` (ML Workflow, drag & drop), `cloud` (Cloud: AWS / Azure / GCP, drag & drop).
- After adding subjects, grant them to existing proctors once the new backend is live: `npm run grant-new-subjects -- --apply` in `backend/` (dry-run without `--apply`).
- Question id = `<subject>-<difficulty>-<slug(title)>`, e.g. `dsa-easy-reverse-the-words`. Ids are what attempts reference. Don't rename titles of live questions.

## Sealed bank (answers need a code)
`build.js` encrypts every question's answers (hidden tests, MCQ `correct`, UI check sources) with AES-256-GCM into a `sealed` blob; statements, constraints, examples, sample tests and config stay public (proctors can read them). Per-question key = HMAC-SHA256(`BANK_MASTER_KEY`, `hpai-bank-v1:<id>`).
- **`BANK_MASTER_KEY` (64 hex chars) is required to build**: set it in the environment or in `backend/.env`. The same value must be set on the backend (Render env var `BANK_MASTER_KEY`), because the API derives and releases keys per attempt / to an admin who re-enters their password.
- Changing the master key = rebuild the bank (`npm run build-bank`) and redeploy frontend + backend together. Never commit the key (`.env` is gitignored).
- `build.js` fails if a hidden test, an MCQ `correct`, a UI check source or a `reference` / `reference_sql` / `solution` key would be readable in the output, and round-trip decrypts every question (a wrong key must fail).
